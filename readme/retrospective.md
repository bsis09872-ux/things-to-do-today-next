## 가장 어려웠던 점 : 한 파일이던 코드를 역할별로 나누기

1차 과제는 `todo.js` 하나에 데이터 · 화면 그리기 · 이벤트가 다 들어 있었습니다. 이걸 **app 라우팅 폴더와 도메인 구조**로 나누면서 컴포넌트를 쪼개는 게 가장 어려웠습니다.

### 1. `'use client'`와 `'use server'` 나누기

처음에는 두 표시가 "서버 컴포넌트 / 클라이언트 컴포넌트" 짝이라고 생각했습니다. 실제로는 뜻이 달랐습니다.

| 표시            | 뜻                                                 | 이 프로젝트에서                                                     |
| --------------- | -------------------------------------------------- | ------------------------------------------------------------------- |
| (아무것도 없음) | 서버 컴포넌트. App Router의 기본값                 | 목록 · 상세를 불러오는 page, 내용만 보여 주는 `TodoDetail`          |
| `'use client'`  | 브라우저에서도 돌아야 하는 컴포넌트                | 클릭 · 입력 · 낙관적 업데이트가 있는 `TodoDashboard`, `TodoForm` 등 |
| `'use server'`  | 브라우저에서 부를 수 있는 **서버 함수(서버 액션)** | 등록 · 수정 · 상태 변경 · 삭제 액션                                 |

특히 `'use server'`를 붙인 함수는 **누구나 호출할 수 있는 공개 주소**가 된다는 걸 알고 나서, 조회 함수에서는 빼고, 액션마다 로그인과 입력값을 다시 검사하도록 바꿨습니다.

### 2. 액션과 화면 컴포넌트 나누기

"버튼을 누르면 DB를 바꾼다"를 한 컴포넌트에 다 넣고 싶었지만, 결국 이렇게 나눴습니다.

```
page (서버)          : 데이터를 불러와 props로 넘김
└ TodoDashboard (클라이언트) : 클릭을 받아 액션을 부르고, 화면을 먼저 바꿈
   └ TodoItem               : props로 받은 걸 그리기만 함
actions (서버)       : 로그인 확인 → 입력값 검사 → DB 변경 → 화면 새로 그리기
```

처음에는 파일이 많아져서 오히려 복잡해 보였습니다. 하지만 기능을 추가할 때 **어디를 고쳐야 하는지 바로 보여서** 7단계에서 필터 · 핀 · 휴지통을 붙일 때는 훨씬 빨랐습니다.

### 3. 공통 부품은 오히려 편했다

버튼 · 입력칸 같은 공통 부품은 shadcn/ui로 이미 있어서, 1차 과제처럼 하나하나 만들 필요가 없었습니다. `FieldError` · `FormMessage`도 로그인 폼에서 만든 걸 할 일 폼에서 그대로 다시 썼습니다.

## 디자인 : 1차 과제의 옷을 그대로 입히기

1차 과제의 **글로벌 CSS와 파비콘(Tdl 로고)**을 가져와서, AI의 도움을 받아 디자인 토큰으로 옮겼습니다.

- 토마토 · 풀 블루 · 레몬 · 종이색 · 잉크 색을 CSS 변수로 정의하고, shadcn/ui의 테마 변수(`--primary`, `--background` 등)에 연결했습니다.
- 그 결과 버튼 · 입력칸 · 테두리 색이 **한 번에** 바뀌었고, 화면 곳곳의 고정 회색(`text-gray-500`)도 토큰 이름으로 바꿔서 이제는 `globals.css` 한 곳만 고치면 됩니다.
- 카드 3색 반복, 완료 시 바래는 카드와 빨간 취소선도 1차 과제 CSS를 거의 그대로 옮겼습니다.

1차 과제에서 배운 "JS는 상태만, 모양은 CSS가"라는 원칙이 여기서도 그대로 통했습니다. `data-done` 속성만 바꾸면 CSS가 카드 모양을 알아서 바꿉니다.

## 에러를 만날 때마다

에러가 날 때마다 처음에는 당혹스러웠습니다. 그런데 하나씩 원인을 찾다 보니, 대부분 **"정상일 때"만 생각하고 만든 부분**이었습니다.

- **리다이렉트**: 로그인 전후, 로그아웃 직후처럼 상태가 바뀌는 순간의 이동을 충분히 생각하지 못했습니다. (로그아웃 후 회원가입이 튕기던 문제)
- **바깥에서 들어오는 값**: 주소창의 `redirectUrl`, `/todo/abc` 같은 id, 서버 액션의 인자처럼 **사용자가 마음대로 바꿀 수 있는 값**을 믿고 있었습니다.
- **실패했을 때**: 조회가 실패하면 빈 배열을 돌려줘서, 문제가 "할 일이 없어요"로 가려졌습니다.

그래서 지금은 기능을 만들 때 "로그인 안 한 사람이 오면?", "값을 조작하면?", "실패하면 화면에 뭐가 보이지?"를 먼저 생각하게 됐습니다. 자세한 내용은 [트러블슈팅](./troubleshooting.md)에 정리했습니다.
